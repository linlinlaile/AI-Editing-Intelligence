# ADR-0013: Benchmark Dataset and Evaluation Contract v1

- Status: Accepted
- Date: 2026-09-13
- Phase: 5.5

## Context

Phase 5.4 completed the first end-to-end observation path:

```text
Artifact Observation
  ↓
Shot Observation aggregation
  ↓
Evidence
  ↓
ContractEvaluator / EvidenceGroundingEvaluator
```

`ContractEvaluator` verifies structural validity: Observation fields, value shape, status and producer identity. `EvidenceGroundingEvaluator` verifies direct Observation-to-Evidence references and run/provenance consistency. These checks answer whether a result is well-formed and traceable, but they do not answer whether the observation matches an accepted annotation, whether a producer is more accurate than another, or whether a change introduced a semantic regression.

Phase 5.4 deliberately did not implement benchmark datasets, annotations, batch evaluation or semantic quality metrics. Without those capabilities, future Observation, temporal or retrieval work would be judged mainly by contract compliance and examples. This conflicts with the project requirement that important capabilities have fixed fixtures, annotation formats or evaluation metrics before quality claims are made.

## Decision

Phase 5.5 defines **Benchmark Dataset and Evaluation Contract v1** as an independent evaluation input and reporting contract. It does not change the Observation, Evidence or EvaluationResult schemas.

### 1. Benchmark dataset

A **benchmark dataset** is a versioned, finite collection of evaluation cases and their annotations. It identifies the benchmark scope, dataset version, annotation version, supported task or feature, and the cases included in the evaluation run.

The dataset is an evaluation asset. It is not part of the Semantic Timeline and does not become an authoritative source of Observation data.

### 2. Annotation

An **annotation** is an externally supplied reference label or structured expected value for one evaluation case. It records the annotation version and the task/feature it evaluates. An annotation may represent an accepted class, set of classes, scalar value, status expectation, or an explicit unknown/not-covered expectation when the task defines those states.

Annotations must identify the case and target they refer to. They must not be stored as model Evidence and must not be interpreted as a claim generated by an Analyzer.

### 3. Benchmark input snapshot

A **benchmark input snapshot** is the immutable, in-memory evaluation input assembled for one benchmark execution. It contains the selected benchmark dataset metadata, evaluation cases and annotations, plus the existing Observation, Evidence and AnalysisRun metadata required by the evaluator.

The snapshot is prepared by the application layer. Evaluators consume the snapshot and do not access repositories, SQLite, media payloads, models or annotation stores directly. A snapshot must be sufficient to reproduce the same metric result for the same metric implementation and versions.

### 4. Evaluation case

An **evaluation case** is the smallest unit that compares an observed result with an annotation. A case identifies:

- a stable case ID;
- the Observation target and feature under evaluation;
- the expected annotation;
- the observed Observation reference or value supplied in the input snapshot;
- optional case metadata needed to define task-specific inclusion or exclusion.

A case may be marked unevaluable when its required Observation, annotation or input provenance is absent. Unevaluable cases must remain visible in reports and must not be silently counted as correct or incorrect.

### 5. Metric result

A **metric result** is a structured result for one metric version over a defined set of evaluation cases. It should contain metric-specific structured result fields, including evaluation counts and metric values where applicable.

Metric results are evaluation outputs. They do not alter Observation status, confidence, coverage, Evidence or AnalysisRun metadata. A metric result may be included in an evaluation report and may be used to compare producer/model/configuration revisions.

### 6. Relationship to EvaluationResult

The existing `EvaluationResult` remains the per-Observation evaluation result defined by ADR-0011. Benchmark metrics and reports may be produced alongside `EvaluationResult`, but this ADR does not add fields to or change the `EvaluationResult` schema. Contract and grounding results remain independent from semantic benchmark scores.

## Boundary

Benchmark evaluation has the following strict boundary:

- Benchmark does not produce Observation.
- Benchmark does not modify, overwrite or attach fields to Observation.
- Benchmark does not replace Evidence or become Evidence.
- Benchmark annotations are reference data, not analyzer provenance.
- `BenchmarkRunner` and `BenchmarkEvaluationUseCase` do not rerun analyzers or models.
- `BenchmarkRunner` and `BenchmarkEvaluationUseCase` do not infer missing observations from media payloads.
- Benchmark evaluation does not make a passing metric a permanent semantic fact.

The application layer, through `BenchmarkEvaluationUseCase`, owns dataset loading, snapshot assembly, batch execution and report handling. `BenchmarkRunner` coordinates benchmark execution, while `MetricCalculator` owns metric-specific calculation. The existing Evaluator concept remains responsible for Observation → EvaluationResult evaluation. Domain Observation and Evidence contracts remain independent of benchmark implementation details.

## Versioning

Benchmark outputs must record all three versions below:

### Dataset version

`dataset_version` identifies the membership and identity of the benchmark cases. Adding, removing, replacing or re-keying cases requires a new dataset version.

### Annotation version

`annotation_version` identifies the annotation content and annotation rules for the selected dataset. Correcting a label, changing an expected value, or changing the treatment of unknown/not-covered cases requires a new annotation version.

Dataset and annotation versions are independent: the same dataset may be evaluated against multiple annotation revisions.

### Metric version

`metric_version` identifies the calculation definition, inclusion rules, aggregation method and rounding/reporting behavior of a metric. Any change that can alter a metric result requires a new metric version.

A report is reproducible only when dataset version, annotation version, metric version, evaluator reference and the evaluated producer/model/configuration revisions are retained together.

## Non-goals

This ADR does not define or implement:

- Retrieval benchmarks;
- Temporal benchmarks or temporal coverage metrics;
- Editing recommendation evaluation or editorial preference benchmarks;
- EvaluationResult storage, SQLite tables or migrations;
- A human annotation application or annotation marketplace;
- A universal quality score across unrelated Observation features;
- Automatic quality gates or automatic rejection of analysis runs;
- New Observation features, analyzers, models or Evidence fields.

## Storage

Phase 5.5 keeps the existing storage boundary:

- no new SQLite table;
- no migration;
- no change to Observation storage;
- no change to Evidence storage;
- no change to `observation_evidence`;
- no persistence of EvaluationResult required by this ADR.

Benchmark datasets, annotations, snapshots and reports may be supplied as application-level fixtures or transient files during implementation, subject to a later storage decision if durable persistence becomes necessary.

## Consequences

This decision makes semantic quality measurable without coupling analyzers to their evaluators. It establishes a stable basis for comparing existing Artifact and Shot observations and for detecting regressions before adding new observation dimensions.

The initial benchmark will be limited by the quality and coverage of its annotations. A metric result is evidence about the defined dataset and task, not proof of universal real-world correctness. New task families, including temporal or retrieval evaluation, require their own contract and decision before being added.
